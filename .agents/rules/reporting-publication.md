# Reporting & Publication Rulebook

Errors in reports rarely come from the model. They come from the last step: a number typed into a slide from last month's run, a figure regenerated while the text still quotes the old value, a table that combines a scenario from the current version with one from the previous version because the new run had not finished. Every artifact then looks correct on its own, and the document as a whole describes no model that ever existed.

This rulebook covers every route by which results reach readers: figures, tables, in-text numbers, reports, papers, policy briefs, presentations, and supplementary material. It is model- and domain-agnostic, and builds on the pipeline rulebook (run manifests, releases, pipeline lineage) and the data-integrity rulebook (no fabrication, sourced external data). Concrete numbers are recommended defaults that a project may adapt in its project profile; the rules themselves are not optional. See the statistical rulebook, "How to Read the Numbers in This Rulebook".

---

## Document Tiers

Not every document needs the full apparatus. The tier is declared in the document's configuration or front matter (e.g. `tier: draft`), and decides which rules apply. A document moves up a tier only by meeting the rules of the new tier, never by relabelling.

| Tier | Examples | What applies |
| :--- | :--- | :--- |
| **Exploratory** | notebooks, diagnostic reports, model-building walkthroughs, internal comparison reports | An identity line: the run or fit the results come from, the code commit, and the build date. A visible "exploratory" banner. Numbers may be computed ad hoc inside the document, but are never typed in. Its results are never quoted in a higher-tier document; they are recomputed there. |
| **Working draft** | paper or report drafts circulated within the team | Principle 1, items 1–3 and 7–9 (dynamic numbers, figures and tables, statements asserted or marked as unchecked), Principle 2, item 4 (declared suite), Principle 5 (citations), Principle 6 (agent writing), and a visible draft banner that names the sections not yet checked. |
| **Leaves the team** | submissions, delivered reports, policy briefs, conference talks, public releases | Everything in this rulebook, including the generated technical appendix, the layout checks, the freeze (Principle 2, item 8), and the review checklist. |

- An exploratory or draft document must not be sent outside the team, even "for information". It is promoted first.
- The tier is shown in the document itself (banner or footer), so a reader can tell a draft from a deliverable.

## Principle 1: Results and Model Descriptions Are Dynamic Objects

**Nothing that comes from the model is typed, copied, or pasted.** This covers the results (every figure, table, and number) and the description of the model itself (equations, specification, priors, and computational settings). All of them are generated by code at build time, from the model outputs and from the specification that was effectively run. When the model changes, during development or between releases, smaller or bigger parts alike, rebuilding the document updates every figure, table, sentence, equation, prior, and setting that depends on it, and nothing else has to be edited by hand.

1. **One path from model to document.**

   ```
   specification + outputs of the result suite (Principle 2)
     → report objects: versioned functions that compute each number, table, figure,
       equation and appendix section
       → documents: reports, papers, slides, briefs, supplements, which only reference report objects
   ```

   - Report objects are code in the repository, reviewed like any other code. They read the outputs and the effective specification through one loader (Principle 2, item 4), never through ad hoc file paths.
   - Documents contain no computation beyond formatting. They reference report objects by name.
   - The same report object feeds every document that shows it. A number, equation, or prior that appears in the paper, the brief, and the slides comes from one object, so they cannot disagree.
   - **Report-object bundle (accepted lightweight form).** For a single document or a small project, the report objects may be computed by one build script into one bundle file (e.g. `build_paper_objects.R` → `paper_objects.rds`), which the document reads once. The bundle then serves as the loader and the registry (item 2, Principle 2, item 4), provided that:
     - it carries its identity: suite or fit ID, variant IDs, code commit, build time, and the checksum of every output file it was computed from;
     - the document reads nothing except the bundle (no further model outputs, no other file paths), and stops if the bundle's suite ID differs from the declared one;
     - every value the text shows is an element of the bundle, under a stable name.
2. **In-text numbers are references, not literals.**
   - In literate formats (Quarto, R Markdown, Jupyter), numbers are inline code, e.g. `` `r fmt(res$profit_base, "bn EUR")` ``.
   - In LaTeX, numbers are macros generated from the results (e.g. `\newcommand{\ProfitBase}{22.1}` written by the build into `results_macros.tex`).
   - Behind both sits a **results registry**: a generated table of every reported value with its key, value, unit, rounding rule, the report object that computed it, and the suite and variant IDs. Text references keys; the registry is the single place where a reported value exists.
3. **Statements derived from results are generated or asserted.** Hardcoding is not limited to digits. The following depend on the results and must not be written as fixed prose:
   - directions and signs ("increases", "a loss"), ranks ("the largest region"), comparisons ("twice as high", "above the baseline"), counts ("in 12 of 16 states"), thresholds ("more than 20 %"), and robustness claims ("robust to wider priors");
   - either generate them from the results (conditional text, computed ranks and counts), or keep the prose and add an **assertion** next to it in the build (e.g. `stopifnot(res$delta_profit > 0)` next to "profit increases"), so that the build fails when the results no longer support the sentence.
4. **The model specification is a dynamic object.** Models change while they are developed: a term is added, a likelihood or link changes, a random effect or constraint is dropped, a nesting is restructured. The description in the document must follow automatically.
   - The specification lives in one machine-readable place (a specification object or configuration: likelihood and link, linear predictor terms, random effects and their structure, constraints, nesting, transformations), and the estimation code is built from it, or checked against it.
   - Equations, term lists, and model diagrams in the document are **generated from that specification**, e.g. LaTeX rendered from templates per term type, with symbols taken from one notation table that is shared by all documents.
   - Where an equation is hand-written for readability, it references specification keys, and the build asserts that the written terms match the specification (same terms, same indices, same constraints). A mismatch fails the build.
   - The specification shown is the one **effectively run**, read from the suite's manifest (pipeline rulebook, Principle 14), not the one in the current working copy or in the plan.
5. **Priors are a dynamic object.**
   - Prior tables are generated from the prior configuration resolved in the run: distribution families and parameters per parameter or block, including any data-dependent scaling, as effectively applied.
   - They show each prior on the estimation scale and on the interpretable scale it was elicited on (elasticities, odds ratios, multiplicative effects), with the elicited range, its source, and its version (statistical rulebook A.3).
   - The prior table in `MODEL_LINEAGE.md` and the one in the document come from the same source, so they cannot drift apart.
   - Prior revisions (statistical rulebook C.4) appear automatically, with their version and reason.
6. **Every document gets an automatically generated technical appendix.** A supplement, appendix, or backup-slide section is generated from the suite's specification and manifest, and rebuilt with every build. It contains at least:
   - **Model specification:** generated equations and term definitions for the main model, and for each robustness variant the declared change against it (variant table; pipeline rulebook, Principle 15).
   - **Full prior specification:** every prior, on both scales, with sources and versions (item 5).
   - **Computational and algorithmic settings:** the algorithm (e.g. sampler type, optimizer, solver), its settings (chains, warmup and post-warmup draws, adaptation targets, maximum tree depth, step-size or proposal tuning, initialization, solver tolerances, iteration limits, convergence criteria), and seeds.
   - **Diagnostics summary:** convergence and efficiency per parameter block (statistical rulebook C.1: R̂ and relative ESS distributions, divergences, E-BFMI), solver convergence status and residuals, predictive-check summaries (C.3), for the main model and every variant.
   - **Data and inputs:** input datasets and versions with links to their source cards (data-integrity rulebook).
   - **Software and environment:** language and package versions, system libraries (e.g. GDAL/PROJ/GEOS), code commits, hardware, and runtime.
   - **Identity:** suite ID, variant table, and build date.

   Nothing in the appendix is maintained by hand. A setting that the appendix cannot report automatically is a gap in the manifest, fixed there.
7. **Figures are scripts, not images.**
   - Every figure is produced by a script from report objects and saved by the build. No manual editing in image or slide editors (moving labels, recolouring, cropping data).
   - Labels, class names, units, and colours come from the shared class tables, palettes, and unit definitions, never retyped in the figure script.
   - Axis limits, breaks, and highlighted elements that depend on the data are computed, or set in configuration with a reason, not tuned by hand to the current run.
   - Each saved figure carries its identity: suite and variant IDs and code commit, in the file metadata or a sidecar, and optionally in a small caption line.
8. **Tables are generated end to end.**
   - Tables are produced by code (e.g. `gt`, `flextable`, `kableExtra`, `xtable`, or the language's equivalent) in the final format. No editing in spreadsheets or word processors after export.
   - Column names, units, row order, and footnotes are part of the code.
   - Exported tables (CSV, XLSX for supplements) carry the suite and variant IDs.
9. **Formatting and rounding live in one place.**
   - One set of formatting functions defines units, scaling (thousands, millions, bn), significant digits, decimal and thousands separators, and percentage conventions, and is used by every document.
   - Round only for display, never before computing derived values.
   - Where rounded parts do not add up to the rounded total, say so in a note; do not adjust a part by hand.
   - Precision shown matches what the results support (e.g. not more digits than the Monte Carlo or validation error allows; statistical rulebook C.1 and D.3).
10. **One command rebuilds everything.**
    - A single build entry point (e.g. `make`, `targets`, `quarto render` of a project) regenerates every report object, figure, table, equation, appendix, and document from the result suite.
    - **"Everything" starts at the saved outputs of the suite, not at the estimation.** Fitting the model is the production run (pipeline rulebook, Principle 15); it is run by its own script and may take hours or days. The document build reads its saved outputs and never refits, so a rendering bug cannot cost a posterior, and the document cannot quietly describe a refit that differs from the suite.
    - Keeping the two steps separate does not loosen the rules: the build verifies that the outputs belong to the declared suite (Principle 2, item 4), and a change that needs new estimates goes through the production script.
    - A document that cannot be rebuilt from scratch from the declared suite, in a clean checkout, is not releasable.
    - Before release, rebuild from scratch (no caches) and compare the results registry, the generated specification, and the prior table with the previous build. Every change is listed and explained.
11. **What may be static.**
    - **External values** (official statistics, literature values, policy parameters) are not model outputs, but are not typed ad hoc either: they live in a versioned reference-data file with their source, are cited, and enter the registry like any other value (data-integrity rulebook).
    - **Truly static content** (conceptual explanations, definitions, motivation) contains no result- or specification-dependent statements.
    - **Tools that cannot be generated** (e.g. a slide deck that must be finished by hand): embed only generated figure, table, and equation files, take numbers from the generated registry, and list every manually transferred value with its key, the suite ID, and the date it was checked. Re-check the list against the registry before each delivery.

## Principle 2: One Coherent Result Suite per Document

**A document describes exactly one production run.** Every result in it comes from one declared **result suite**: the outputs of one production run, which contains the main model and its declared robustness variants, all produced by the same production script, code version, and input versions. Outputs of different versions, runs, or specifications are never mixed, either silently or by convenience. Robustness checks are part of the suite, not exceptions to it.

How production runs and variants are made is defined in the pipeline rulebook (Principle 15); which variants to run and how to read them, in the statistical rulebook (D.4). This principle covers how documents use them.

1. **A suite is one production run.** One run ID, with a variant ID per variant (the main specification is `main`), and its variant table (pipeline rulebook, Principle 15). For anything shared beyond the team, the suite is a release (pipeline rulebook, Principle 12). Runs made with a different code or configuration version are a different suite, even if they share a run name.
2. **Variants are presented as what they are.**
   - Headline results come from `main`.
   - Each variant is described by its declared change, taken from the variant table, in the text or the technical appendix (Principle 1, item 6).
   - An architecture variant is presented as a different model, not as a perturbation of the main one.
3. **All declared variants appear in the document.** Including those that change the conclusion, and those that failed diagnostics, which are shown as failed with their diagnostics instead of estimates. Variants added after results were seen are marked as such (statistical rulebook D.4, items 3–4).
4. **The document declares its suite, and every load is checked against it.**
   - The suite ID is set once, in the document's or project's configuration. It is never discovered ("latest run", "newest folder", "most recent file").
   - All report objects read the outputs through one loader that verifies, for every file, that its run ID, variant ID, specification hash, and checksum belong to the declared suite. A mismatch, or a file without identity, stops the build.
   - Only variants that passed the assembly checks of the production run (pipeline rulebook, Principle 15, item 5) can be loaded.
   - The document shows its suite: suite ID, code commit, and date in a footnote, appendix, colophon, or slide footer, and the variant table in the technical appendix.
5. **Variants are labelled throughout the document.**
   - Every robustness figure, table, and value names its variant ID (or a label generated from it). Registry keys include the variant ID.
   - Robustness statements ("the effect is robust to wider priors", "the ranking does not change without the spatial effect") are asserted in the build (Principle 1, item 3), following the reading rules of statistical rulebook D.4, item 5.
6. **Comparisons with other suites are the explicit exception.** Comparing with a previous release, or with a model that is not part of the production run, is allowed when declared:
   - each suite is declared with a label and a role (e.g. "main", "previous release");
   - every element that combines suites states which suite it comes from, in its labels or caption;
   - comparisons are made only along the declared dimension; if the suites also differ in other respects (e.g. both the prior and the input data changed), the document says so.
7. **No gap filling across suites, and no partial updates.**
   - If a scenario, region, period, variant, or indicator is missing from the declared suite, it is missing from the document, or the suite is completed through the production script. Taking the missing piece from another version or run is forbidden, as is substituting an older figure "until the new run is done". Mark it as pending instead.
   - A rerun of any stage or variant makes a new suite (pipeline rulebook, Principle 15, item 6), and the whole document is rebuilt from it.
   - Report caches (knitr or Quarto caches, `targets` stores, notebook outputs, saved figure files) are keyed by the suite ID, and are cleared or invalidated when it changes. A stale cache is a form of mixing.
8. **Submitted and published documents are frozen to their suite.**
   - A document that leaves the team (submission, report delivery, conference talk) is tied to a frozen suite and a tagged build of the document code.
   - A revision (e.g. after review) produces a new suite through the production script and rebuilds the whole document. Updating only the figures or numbers that "changed" is forbidden.
   - The revision includes a change log generated from the diff between the two suites: changed values, specification, priors, settings, and variants, with the reasons.
9. **Earlier results are cited, not mixed.** Statements about earlier releases or earlier reports ("in our 2025 report, profit was ...") are labelled as such and come from that suite's frozen registry or publication, not from a re-typed value or a different run.

## Principle 3: Layout Within the Margins & House Style

Every document object (figure, table, equation, algorithm, code listing, map) fits the document it is placed in, and all documents share one visual and notational style. The style leans on the conventions of econometric and Bayesian statistical writing: models written as generative probability statements, a fixed notation, posterior summaries instead of significance stars.

1. **Every object stays within the margins.**
   - Each output format has one **layout profile** in the configuration: text width and column width (single and double column), text height, slide safe area, base font size, and fonts. Report objects read it; nothing hard-codes sizes per figure.
   - **Figures are generated at their final physical size** (e.g. `width = textwidth` or `columnwidth`, in cm or inches), with font sizes matched to the body text (typically the caption size or one step smaller), and placed without rescaling. A figure scaled down to fit has unreadable labels; one scaled up has inflated ones.
   - **Tables fit the text width.** Use abbreviations defined in a note, wrapped headers, fewer columns, a split table, or a landscape page, in that order of preference. Shrinking below a minimum font size (e.g. `\footnotesize` in papers) to make a table fit is not allowed.
   - **Equations fit the text width.** Long expressions are broken over lines (`aligned`, `multline`, `split`) at operators, with consistent alignment, or defined in parts (e.g. the linear predictor $\eta_{it}$ first, then the likelihood).
   - **Slides:** objects stay inside the safe area of the slide template, with font sizes legible from the back of a room (a minimum point size in the layout profile).
   - **The build checks it.** LaTeX overfull boxes above a small tolerance, figures whose saved size differs from the profile, and tables or equations exceeding the text width fail the build or are listed in the build report. Every format of a document (paper, preprint, slides, brief) is checked against its own profile.
2. **Model descriptions follow econometric and Bayesian conventions.**
   - **Generative form.** Models are written as probability statements, from the data level to the priors:
     $$y_{it} \sim \operatorname{Poisson}(\mu_{it}), \qquad \log \mu_{it} = \alpha + \mathbf{x}_{it}^{\top}\boldsymbol{\beta} + u_i + \log E_{it}, \qquad u_i \sim \mathcal{N}(0, \sigma_u^2),$$
     $$\boldsymbol{\beta} \sim \mathcal{N}(\mathbf{0}, s_\beta^2 \mathbf{I}), \qquad \sigma_u \sim \operatorname{Half-Normal}(0, s_u).$$
     Hierarchical models are presented layer by layer (data model, process or latent model, parameter model), with the link, offsets, constraints (e.g. sum-to-zero), and identification restrictions stated explicitly.
   - **One notation table** (Principle 1, item 4) shared by all documents: scalars in italics, vectors and matrices in bold (lower and upper case), parameters in Greek, data in Latin letters, indices fixed per dimension (e.g. $i$ unit, $t$ time, $r$ region, $k$ class), estimation-scale quantities marked as in the statistical rulebook (e.g. $\tilde{\mathbf{X}}$), distributions in upright type with standard parameterizations stated once (e.g. whether $\mathcal{N}$ takes a variance or a standard deviation).
   - **Every symbol is defined** at first use or in the notation table, with its unit or scale.
   - **Econometric quantities are named as such:** the estimand (e.g. average marginal effect, elasticity, direct and indirect spatial effects), the scale it is reported on, and how it is computed from the posterior (statistical rulebook D.3).
   - **Computational descriptions** use an algorithm environment or a structured list (sampler or solver, blocks or steps, settings), generated from the manifest (Principle 1, item 6).
3. **Results tables follow the posterior-summary convention.**
   - The Bayesian analogue of an econometric coefficient table: per parameter or estimand, a posterior central value (mean or median, stated), posterior standard deviation, a credible interval (level stated, e.g. 90 % or 95 %), and, where used, $p_d$ and the ROPE result (statistical rulebook D.1, D.2). Convergence columns ($\hat{R}$, relative ESS) appear in the appendix or as a compact column.
   - No significance stars and no $p$-value thresholds. Evidence is reported continuously (statistical rulebook D.1).
   - Model-comparison tables report $\widehat{\text{elpd}}_{\text{loo}}$ differences with standard errors, and predictive measures as in statistical rulebook C.3.
   - Grouping rows by parameter block (fixed effects, random-effect scales, spatial parameters), units in headers, and the estimation scale (e.g. log-odds, elasticity) in the caption or column header.
4. **Figures follow a restrained statistical style.**
   - Preferred forms for model results: interval plots of estimands (coefficient or forest plots with credible intervals), posterior densities where the shape matters, posterior predictive checks, PIT or calibration plots, and maps with an explicit uncertainty layer or statement.
   - One theme for all figures: no decoration that carries no information (3D effects, heavy grids, shadows), axis labels with units, consistent ordering and colours of classes, variants, and scenarios across figures, colour-blind-safe palettes, and sequential or diverging palettes chosen by the data type.
   - Typography matches the document: the same font family (or a matching one) for figure text and math, so symbols in figures look like those in the equations.
5. **One house style, set in templates.** Fonts, colours, the notation table, the layout profiles, table and figure themes, and caption conventions live in shared templates (e.g. a LaTeX class or preamble, a Quarto extension, a plotting theme, a table theme) used by every document. A document does not restyle objects locally.

## Principle 4: Sources and Rendered Files in Version Control

A document has exactly one source. Rendered files (HTML, PDF, DOCX, slide exports) and the intermediates a renderer writes (e.g. the `.tex` file kept by Quarto's `keep-tex`, `*_files/` folders, knitr caches) are build products.

1. **Generated files are never edited.** A correction is made in the source and the document is rebuilt. An intermediate that was edited by hand has become a second source that the next build overwrites, or that silently drifts from the real one.
2. **Rendered files are not committed as working files.** They go into `.gitignore` (or a build directory that is ignored). A committed rendered file next to its source is out of date as soon as either changes, and readers cannot tell which one is current.
3. **Rendered files that must be kept are release artefacts.** A submitted or delivered version (Principle 2, item 8) is kept as a tagged release, or in a release directory with the suite ID and build tag in the file name, together with its checksum. It is never overwritten.
4. **Intermediates kept on purpose are marked as generated.** If a journal requires the `.tex`, it is produced by the build and stored with the release, with a header line stating that it is generated and from which source and commit. It is not edited for the submission; changes go through the source.
5. **Large figure files and data used by the document** follow the same rule: generated by the build, not committed, unless they are part of a release.

## Principle 5: Citations and Claims About the Literature

A fabricated or misattributed citation is fabrication (data-integrity rulebook, Principle 1).

1. **Every citation key resolves.** The build fails on a key that is missing from the bibliography file, and lists entries that are never cited.
2. **Every bibliography entry is verified** against the publisher's record, a DOI resolver, or the document itself: authors, year, title, venue, volume and pages, DOI. An entry that cannot be verified is marked as unverified and does not appear in a document that leaves the team. Entries are never completed from memory.
3. **A claim attributed to a source is checked against that source.** "X find that ..." states what the source shows, with the page, table, or section where it matters (e.g. a parameter value, a range, a method). Agents never attribute a finding to a paper they have not read, and say so when they could not check it.
4. **Numbers taken from the literature** are external values (Principle 1, item 11): they live in the versioned reference-data file with their source and location, and enter the registry from there.
5. **Software is cited too:** packages and tools that the results depend on, with the versions that were run (from the manifest).

## Principle 6: Agents Writing Documents

When a coding agent drafts or edits a document:

1. **No values without a source in the build.** If the registry or the bundle has no value for a number the text needs, the agent adds a visible placeholder that fails the build at the "leaves the team" tier (e.g. `\TODO{key: profit_base}` or an inline call to a missing key), and lists it. It never writes a plausible-looking number, and never copies a value from the console, an earlier draft, or another document.
2. **Result-dependent statements are added with their assertion** (Principle 1, item 3), or marked as unchecked in the draft banner.
3. **Prose about the model follows the specification and the code**, not the plan or memory. When the two disagree, the agent reports the disagreement instead of choosing one.
4. **Changes to a document that leaves the team are listed:** what changed, which values or claims were affected, and which checks were rerun. Edits that change a conclusion are flagged to the authors.
5. **The agent states what it did not check** (data-integrity rulebook, Principle 3): citations it could not verify, figures it did not inspect at final size, claims it could not assert.

## Reporting Review Checklist

Before a report, paper, brief, or presentation leaves the team:

- [ ] **Tier:** declared and shown in the document; only "leaves the team" documents go outside the team.
- [ ] **Dynamic objects:** every number, figure, and table is generated from report objects; no typed, copied, or pasted results; result-dependent statements are generated or asserted.
- [ ] **Specification and priors:** equations, term lists, and prior tables are generated from the effectively run specification and prior configuration, or asserted against them; notation from one shared table.
- [ ] **Technical appendix:** generated, complete (specification and variant changes, full priors, algorithm settings and seeds, diagnostics per variant, inputs, software and environment, identity), and nothing in it maintained by hand.
- [ ] **Registry:** every reported value is in the results registry with unit, rounding, source object, and suite and variant IDs; external values are sourced and cited.
- [ ] **Formatting:** one formatting layer; rounding at display only; precision supported by the results.
- [ ] **Figures and tables:** produced by scripts end to end; labels, colours, and units from shared tables; no manual post-editing; files carry their suite and variant IDs.
- [ ] **Rebuild:** one command rebuilds everything from the suite's saved outputs (no refit) from a clean checkout without caches; the diff of registry, specification, and priors against the previous build is reviewed.
- [ ] **One production run:** the suite ID is declared (not discovered), shown in the document, and every loaded file is verified against it.
- [ ] **Variants:** from the production run's variant table (pipeline rulebook, Principle 15; statistical rulebook, D.4); all declared variants shown, failed ones as failed; architecture variants presented as different models; every robustness element labelled with its variant; robustness claims asserted.
- [ ] **No mixing:** no outputs from other versions, runs, or specifications; no gap filling across suites; no partial reruns; no stale caches.
- [ ] **Comparisons with other suites:** declared with label and role, every combined element labelled, differences beyond the compared dimension stated.
- [ ] **Freeze:** submitted documents are tied to a frozen suite and a tagged build; revisions rerun the production script, rebuild everything, and include the generated change log.
- [ ] **Margins:** every figure, table, equation, and listing fits the text or column width (or slide safe area) of each output format; figures generated at final size with matching fonts; no shrinking below the minimum font size; the build reports no overfull objects.
- [ ] **House style:** models in generative form with the shared notation table and every symbol defined; posterior-summary tables without significance stars; one figure and table theme; fonts and math typography consistent across text and figures.
- [ ] **Sources in version control:** one source per document; rendered files and intermediates not edited and not committed as working files; delivered versions kept as tagged release artefacts.
- [ ] **Citations:** every key resolves; every entry verified; attributed claims checked against their sources; software cited with versions.
- [ ] **Agent edits:** no values without a source in the build; placeholders fail the build; unchecked items listed.
- [ ] **Manual exceptions:** any manually transferred value is listed with key, suite ID, and check date, and was re-checked against the registry.
